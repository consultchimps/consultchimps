[Open the database tool](/tools/db) to create or open a local database, define
tables, and import Excel workbooks. The CLI exposes the same operations under
`consultchimps db`.

The working database stores accepted rows and import history. Excel files are
inputs, not the continuing source of truth. A saved import batch contains the
captured values needed to review and apply an import after the original
workbooks are no longer available.

In the browser, reopen the working database after a reload and choose **Resume**
under **Saved import reviews**. The database tool discovers its saved batches in
browser storage and reconstructs the review from captured rows, so it does not
need to read the Excel files again.

Browser preparation reports success after closing its workbook sources. If
`DB_BROWSER_IMPORT_CLEANUP_REQUIRED` appears, retry **Prepare review** to finish
releasing retained workbook or private-batch resources. Preparation retries that
cleanup before opening new sources. Keep the tab open while retrying so the
worker retains the handles needed for cleanup.

The browser disables application while destination, column mapping, or type
decisions differ from the accepted review. Review the edited decisions again
before applying them.

## Choose a database format

Use DuckDB for analytical SQL involving scans, joins, grouping, and calculated
expressions. Use SQLite when compatibility with SQLite applications is the
priority. Both are persistent file formats. Engine memory still holds working
buffers, but opening and saving do not require a JavaScript copy of the whole
database.

In the browser, **Open database file** creates a working copy with a generated
name by default. Enter an **Imported working copy name** to choose a name. To
refresh a saved copy, enter its name and select **Replace an existing browser
working copy with this name**. Replacement affects browser storage; the selected
file stays unchanged. Leave replacement unchecked to keep an existing copy.
Generated working-copy names and inferred Record ID prefixes keep Unicode
characters intact when shortened.

**Browser working copies** lists every working copy stored in this browser, read
from storage rather than from a remembered list, with the most recently used
first. Each copy can be opened or deleted; the open copy offers **Close**
instead. Deleting removes that copy's files from browser storage and leaves
opened and exported files alone. Saved import batches belong to a database ID,
not a name, and remain until the database that owns them lists and discards
them. The section also shows how much site storage the browser reports in use. A
name stored in both formats, or a DuckDB write-ahead log without its database,
is listed with the code opening it would raise.

SQLite triggers on managed tables or internal bookkeeping tables can change
imported rows and receipts. Managed writes reject these triggers with
`DB_SCHEMA_DRIFT`. Restore the declared schema before retrying.

A file created by ConsultChimps includes ordinary data tables and reserved
`_consultchimps` metadata tables. Keep the metadata when working in another
application: it carries schema definitions, generated ID counters, source
captures, and batch history. Arbitrary third-party databases do not acquire this
metadata merely by being opened.

Opening a managed database checks its supported format version and required
internal tables and columns. If that structure is damaged, restore a verified
copy before importing more data.

This phase supplies database management and import operations. A general query
editor, editable analytics grid, charts, automatic record reconciliation, and
master dataset maintenance are outside this phase.

## Create a database and capture workbooks

```bash
consultchimps db create -o inventory.duckdb
consultchimps db import prepare inventory.duckdb --input north=north.xlsx --input south=south.xlsx -o review.ccplan
consultchimps db import inspect review.ccplan
consultchimps db import apply inventory.duckdb --batch review.ccplan
consultchimps db inspect inventory.duckdb
```

Commands print labeled summaries, review details, and next steps by default. Add
`--json` for structured output used by scripts.

Use `.sqlite` for a SQLite database. A filename without a recognized extension
requires `--format sqlite` or `--format duckdb`. Creation refuses an existing
output unless `--force` is supplied. Replacing an input with an output is
refused even with `--force`.

`db import prepare` writes a private staging file; it does not add the captured
rows to the working tables. `db import inspect` shows its routes, column
mappings, row counts, conflicts, and a bounded preview using a read-only handle.
`db import apply` approves a resolved batch and commits its rows. Keep `.ccplan`
files as carefully as the workbooks because they contain source values.

An already-ready batch is opened read-only during `db import apply`. A batch
that still needs automatic resolution is reopened writable so its review can be
updated. If a batch is missing, inaccessible, or not a supported batch file,
opening it returns `DB_INVALID_PREPARED_IMPORT`. Check the path and access,
restore a verified copy, or prepare the workbook again.

For a repeated import, preview the reused rows with
`consultchimps db import inspect review.ccplan --database inventory.duckdb`.
These rows remain in the working database instead of being copied into the batch
again. Without `--database`, inspection reports preview warnings for reused
selections. The original Excel files are not needed for either preview.

New preparations also compare the workbook reader version. This release reads a
file again if its only saved capture came from the older reader, then presents
the new capture for review. Earlier imported rows and history are retained; they
are not automatically corrected or replaced.

Use `db import inspect --limit <number>` to choose the preview page size. When
more rows are available, pass the reported next preview cursor to `--cursor`,
quoted for your shell. The cursor continues the saved preview without reading
Excel.

Route summaries use a separate page. The CLI defaults to 50 routes and accepts
from 1 to 100 with `--route-limit`; pass the reported next route cursor to
`--route-cursor`. In the browser, use **First routes** and **Next routes**. A
route cursor belongs to one batch revision and review fingerprint. Updating the
profile invalidates it, so return to the first route page after an update.
Unsaved destination or column edits disable route paging and application until
**Update review** stores and validates those decisions.

An import review distinguishes two totals. Captured rows are rows newly stored
in the private batch; review rows also include captures reused from the working
database. Library inspection also reports the target database revision it
observed and the capture IDs of an applied batch. The browser uses this saved
review state rather than rebuilding it from the current form.

For an import whose routing is already explicit, `db import run` combines
preparation and application. Use a saved batch when a submission needs review or
corrections.

## Select worksheets, tables, and ranges

The default selection uses visible worksheets with the first row as the header.
Use `--hidden` to include hidden worksheets, or `--header-row` to change the
default header row. Chart sheets are not importable tables and do not prevent
selecting an ordinary worksheet in the same workbook. Automatic imports reject a
selection with no eligible regions before recording an import. For example, a
workbook containing only hidden worksheets needs `--hidden`. A single workbook
can instead select one region:

```bash
consultchimps db import prepare inventory.duckdb --input north=north.xlsx --sheet Inventory --header-row 3 -o north.ccplan
consultchimps db import prepare inventory.duckdb --input north=north.xlsx --table InventoryTable -o table.ccplan
consultchimps db import prepare inventory.duckdb --input north=north.xlsx --range "'Inventory'!B3:F200" -o range.ccplan
```

The streaming reader supports OOXML workbooks (`.xlsx` and `.xlsm`). Macros do
not run. It reads formula caches, without calculating formulas. Missing caches
and error cells need an explicit correction before they can become typed data.
Custom number formats use the section selected by the cell's value when
identifying dates. A condition only in the second section, or a condition after
the second section, is unsupported. Preparation reports an error for those
layouts; simplify the number format in a copy of the workbook before retrying.

Styles needed to interpret Excel dates are read; workbook formatting and macros
are not database content. Elapsed formats such as `[h]:mm` retain their numeric
day fractions instead of becoming calendar dates. Missing declared style parts
and invalid style references fail before those values can be interpreted.
Invalid date-system flags and unknown worksheet visibility states also stop
preparation instead of selecting a default interpretation. Duplicate or
malformed number-format IDs, missing format codes, and references to undefined
custom formats also fail instead of treating the cells as ordinary numbers.

Each column in an explicit or named range needs a header. Worksheet selections
use the span from the first populated header to the last, and reject blank
headers inside that span. Name missing headers or choose a narrower range before
retrying. Duplicate cell coordinates and ambiguous worksheet or Table names are
rejected instead of selecting one value or region.

## Route different submissions to tables

A profile is a versioned JSON document. Each route identifies an input alias,
its selection key, a destination table, and source-to-target column mappings.
The batch review exposes these keys and inferred columns. A worksheet selection
key encodes both its name and header row, so changing a header row changes the
capture definition.

Map a destination column at most once within a route. Target names that differ
only in letter case refer to the same column. Invalid table names, Record ID
settings, and duplicate explicit destination mappings are rejected before
workbook capture begins. Automatic mappings are checked against the captured
headings before a batch can become ready.

This synthetic profile appends a selected worksheet to an existing table:

```json
{
  "version": 1,
  "routes": [
    {
      "source": "north",
      "selection": "{\"sheet\":\"Inventory\",\"headerRow\":1}",
      "destination": { "kind": "existing-table", "table": "datasets" },
      "columns": [
        { "source": "Dataset name", "target": "name", "type": "text" },
        {
          "source": "Attribute count",
          "target": "attributes",
          "type": "integer"
        }
      ]
    }
  ]
}
```

```bash
consultchimps db import prepare inventory.duckdb --input north=north.xlsx --profile profile.json -o north.ccplan
consultchimps db import update inventory.duckdb --batch north.ccplan --profile corrected-profile.json
consultchimps db import apply inventory.duckdb --batch north.ccplan
```

Use `new-table` with an explicit schema to create a destination, or
`new-table-infer` with a name and Record ID configuration to propose a schema.
For an inferred table, explicit mappings also choose the proposed column names
and types. These mappings are retained when you approve the schema. For example,
map a source column named `record_id` to `vendor_id` to keep it separate from
the database's generated Record ID. An existing table name is a decision to
review, not permission to replace that table. Resolving a captured batch changes
routing without reading Excel again. `db import update --profile` replaces the
saved batch's table routes. A selection omitted from the replacement profile is
excluded from table loading. Its captured rows remain in the batch and become
received evidence in the managed database and are linked to a batch when one is
recorded during apply.

If another import changes the database after you prepare a batch, re-review its
captured data against the current database before applying it:

```bash
consultchimps db import update inventory.duckdb --batch north.ccplan
consultchimps db import inspect north.ccplan --json
consultchimps db import apply inventory.duckdb --batch north.ccplan
```

Changed submissions append source observations. Matching names, vendor IDs, or
row hashes do not silently merge business records. Generated Record IDs identify
stored observations independently of vendor identifiers; deciding that several
observations represent one real dataset is a later reconciliation operation.

## Define schemas first

Save a schema as JSON, then create a database with `--schema schema.json` or use
`db schema apply`. The dry run reports proposed additions without writing them.

The browser lists the tables and columns proposed for creation before approval,
including their types and constraints. Editing the schema document requires a
new review.

If `DB_BROWSER_SCHEMA_PERSISTENCE_REQUIRED` appears, the schema changes were
applied, but the browser could not finish saving the database. The table list
reflects the applied changes, and the previous review is cleared. Keep the tab
open and export the database again to retry saving it. Do not reapply those
schema changes.

```json
{
  "version": 1,
  "tables": [
    {
      "name": "datasets",
      "recordId": { "prefix": "DS", "padding": 6 },
      "columns": [
        { "name": "name", "type": "text", "nullable": false },
        { "name": "attributes", "type": "integer" }
      ],
      "foreignKeys": []
    }
  ]
}
```

```bash
consultchimps db schema apply inventory.duckdb --file schema.json --dry-run
consultchimps db schema apply inventory.duckdb --file schema.json
```

Types are `text`, `integer`, `real`, `decimal`, `boolean`, `date`, and
`timestamp`. A decimal column declares `precision` and `scale`. A foreign key
names a local column and `referencesTable`; it refers to that table's generated
`record_id`. Several columns can refer to different tables. This does not
resolve vendor identifiers into those generated IDs automatically.

Date-only source values infer a `date` column, including declared Excel dates
with cached formula values. A column containing dates and timestamps infers
`timestamp`; date-only entries become midnight values. An explicit timestamp at
midnight remains a timestamp.

## Keep duplicate content and batch history separate

The importer hashes source bytes. Previously captured content can be reused when
the reader version and selected region agree, including when a file is renamed.
This avoids extracting and inserting the same captured observations again. A
changed file is a new source capture; it is not assumed to be a full snapshot or
a list of changes.

Reusing rows in the same table requires the same effective column mapping. A
changed mapping returns `DB_IMPORT_APPLICATION_CONFLICT` before commit, so a new
profile cannot silently claim that earlier observations were remapped. Choose a
new destination table to retain another interpretation of the same captured
source.

This check also covers aliases within one batch. If aliases reuse one captured
selection but map it differently into the same table, the batch needs review.
Correct the mappings or select separate destination tables before applying;
matching alias routes can reuse one application.

The browser's no-new-observation-rows notice requires the reviewed captures,
destination tables, and mappings to match existing applications. Reusing source
content alone does not meet that condition. Editing a route hides the notice
until the updated review confirms reuse.

The browser distinguishes selected workbooks that share a filename. Their roles
and revisions remain separate source details, while matching content can still
reuse captured rows.

Applied batches retain their reviewed column routes, decisions, and source
bindings in the database. Removing the private batch file does not remove that
applied audit history.

In an external SQL tool, group observations by `_source_file_id` to compare
submitted files. For a table named `attributes` with a boolean `is_cde` column:

```sql
SELECT _source_file_id,
       COUNT(*) AS attribute_rows,
       SUM(CASE WHEN is_cde THEN 1 ELSE 0 END) AS reported_cde_rows
FROM attributes
GROUP BY _source_file_id;
```

These are counts of submitted observations. They do not resolve duplicate
business identities or choose an authoritative CDE classification.

A batch is a separate event referencing captures. The same content can belong to
another batch without duplicating its row values. Context records a label,
dates, declared scope, and optional reported attributes:

```json
{
  "label": "Inventory submission B",
  "scope": { "kind": "partial", "description": "Selected business units" },
  "attributes": { "reportedDatasetCount": 125 }
}
```

```bash
consultchimps db import apply inventory.duckdb --batch review.ccplan --context batch.json --request-id submission-b
consultchimps db import history inventory.duckdb
consultchimps db import record inventory.duckdb --capture CAPTURE_ID --context batch.json --request-id submission-c
```

Use a stable, nonblank request ID when retrying the same action. An intentional
new event needs a new request ID. A standalone batch ID cannot start an import,
and an import-only ID cannot create a separate batch. Those uses return
`DB_REQUEST_ID_CONFLICT` before changing the database. If an import also
recorded a batch, retrying that batch with matching context and captures returns
the existing event. Reported counts remain statements supplied with the batch;
they are not relabeled as counts calculated from imported rows. Scope can be
`full`, `partial` with a description, `changes` with a baseline, or `unknown`. A
partial submission does not remove observations absent from it.

Batch labels, partial descriptions, and change baselines must contain text.
Reported numeric attributes must be finite. Invalid context is rejected before
an import or batch event changes the database.

When you leave a completed event's request ID unchanged, the browser's **Record
another batch** action generates a fresh ID. An interrupted request keeps its
saved ID for recovery. Replaying an existing ID reports that the event was
already recorded.

In the browser's batch history, choose **Refresh** to load the first page and
**Next batches** to view the next page. Each page contains up to 25 events.
Refreshing returns to the first page; opening another database clears the
previous database's history. The reuse notice means an event includes a capture
seen in an earlier batch. The same event can also include newly imported rows.

## Export a copy or convert the format

```bash
consultchimps db export inventory.duckdb -o shared.duckdb
consultchimps db export inventory.duckdb -o compatible.sqlite --dry-run
consultchimps db export inventory.duckdb -o compatible.sqlite
```

An export dry run reports the conversion plan without writing the destination.
It accepts an existing output path, including the source path, without
`--force`. An actual export still validates collisions and refuses to overwrite
its source.

For WAL-mode SQLite sources, read-only inspection and dry runs can create `-wal`
and `-shm` coordination files beside the source database. They do not change its
tables.

An export produces a separate file. A cross-format conversion reports storage
representation changes and refuses objects without a supported mapping. Keep the
working source and verify the output in the receiving application. SQLite stores
exact decimals as text, while DuckDB uses its decimal type; this changes how raw
SQL should interpret those columns.

Decimal inference and decimal column mappings accept exponent notation such as
`1.25E-2` and normalize it to `0.0125` without a floating-point conversion.
Values must fit the destination precision and scale.

A same-format snapshot keeps the logical database ID, so a saved import review
can resume after restoring or moving it when the revision and schema still
match. Converting formats creates a new database ID and requires a new review.
Exported copies do not synchronize. A shared ID does not establish that their
rows remain equal or prevent another copy from being edited.

Cross-format export also checks stored values while copying rows. If another
application has put a value outside a column's registered type, conversion stops
before publishing the output. For example, a SQLite Boolean value of `2` or an
integer value of `1.5` needs correction in the working database before exporting
to DuckDB. A dry run checks schema compatibility; it does not scan rows for
these value errors.

Schema creation supports acyclic relationships to generated Record IDs. Changing
an existing relationship, Record ID configuration, column type, or nullability
requires a separate migration and is reported as a conflict here. External
schema changes invalidate saved schema plans.

`db inspect` can describe table columns in an ordinary SQLite or DuckDB file
without adding ConsultChimps metadata or reading its rows. Managed imports,
batch history, and conversion require a database created by ConsultChimps.

Managed database opening checks the layout and key constraints of its reserved
tables. `DB_CORRUPT_DATABASE` or `DB_INVALID_PREPARED_IMPORT` can indicate an
externally changed internal column or key. Restore a verified database or batch
copy before continuing. This phase does not adopt an arbitrary application's
database for managed writes.

## Browser storage and exported files

The browser workspace uses persistent origin-private storage (OPFS). Opening an
OS file creates a browser working copy. Subsequent imports and schema changes
modify that working copy. They do not synchronize back to the selected file.
Export a new file when another application needs the current database.

The database tool is verified in Chromium-based desktop browsers such as Chrome
and Edge. Other browsers that provide origin-private file storage are untested.
Use the tool in one tab or window at a time: the working database keeps
exclusive file handles, so a second tab of the same site shows a notice and
takes over on its own once the first tab is closed. A closed tab can keep its
file handles for a short while; the next action waits for them with a progress
message before it starts the engine. If the engine still cannot start, the tool
reports `DB_BROWSER_ENGINE_UNAVAILABLE` with the browser's reason and starts
again on the next action once the cause is resolved.

If browser replacement reports a temporary-file cleanup error, inspect its
outcome before retrying. `published: true` means the new working copy is already
stored under the reported public name. The error also lists private candidate or
backup names that may remain. Resolve the storage issue and release any
remaining handles before reopening the working copy.

Cancelling browser replacement during copying attempts to restore the previous
working copy. If an open fails with `DB_BROWSER_OPEN_CLEANUP_REQUIRED`, retry
opening it to release the retained handles. If that cleanup still fails, reload
the page before replacing or removing the reported copy.

Browser storage belongs to the site's origin and browser profile. Clearing site
data removes it, and private browsing or storage quotas can prevent persistence.
Keep exported files as backups. The interface checks capabilities and reports
unsupported storage instead of falling back to loading the whole database into
memory.

A browser download keeps a temporary export in OPFS while the browser consumes
the file. Its name carries a 24-hour expiry. The workspace checks for expired
export files when it starts and once an hour, and removes only files in its
private export namespace. A Web Lock protects an export while another tab is
writing or downloading it. When Web Locks are unavailable, cleanup leaves the
file in place instead of risking an active download. These temporary files need
browser storage in addition to the working database until cleanup completes.

Saved reviews use prepared artifact format 3. The application checks a stored
fingerprint of the reviewed metadata before using a batch. Capture checksums
also bind row coordinates and values to the review. Editing a batch outside the
review workflow can invalidate these checks. Apply verifies rows as it copies
fresh captures or uses stored captures for a new table application, and rolls
back on a mismatch before commit. Receipt-only retries do not rescan rows. These
checks are not digital signatures. Version 1 and 2 spike batches must be
regenerated from the original sources; working database files keep their format.

Saved import reviews use the same browser storage. If a tab closes or an apply
is cancelled, reopen the working database and resume the saved review. A
cancelled apply rolls back its transaction, so retrying the batch does not keep
a partly written batch.

If loading saved reviews reports a cleanup failure, keep the tab open and choose
**Retry saved imports**. The tool retries retained handles before listing the
reviews again.

A saved batch containing rows from an unfinished capture is rejected when it
reopens. Prepare the original sources again or restore a verified batch copy.
Opening the damaged batch does not delete it.

The browser saves an import request before applying it. If the database commits
but the worker response is lost, reopen the database and choose **Finish
recovery**. The workspace replays the same request ID and returns its saved
receipt instead of adding the rows or batch again. If that request returns
`DB_STALE_IMPORT_PLAN`, the tool clears the pending request and unlocks the
review controls. Load the current saved review, update its mapping if needed,
and review it again before applying.

The CLI works directly with the named database file. Use one writer at a time,
close a database in other applications before modifying it, and retain the
source files or private batches until an import is verified. When replacing an
exported file with `--force`, keep other applications from writing that
destination until export finishes. Use a new filename if exclusive access is
uncertain.

Cancelling a CLI export before file publication leaves the destination unchanged
and attempts to remove the private staged copy. Cancellation is no longer
checked once file publication begins.

`CLI_DB_IMPORT_CLEANUP_REQUIRED` reports a one-step import whose local resources
could not finish closing or being removed. Its details include
`operationCompleted` and any private batch directory. Inspect a completed import
before repeating it. `CLI_DB_INPUT_CLEANUP_REQUIRED` retains failures to close
workbooks, input files, or scratch storage.

Database commands delay their result until required cleanup finishes, so
`--json` emits a single result or error envelope. If another database command
commits its result but cannot close its resources,
`CLI_DB_COMMAND_CLEANUP_REQUIRED` identifies the operation and recovery paths.
Inspect those files before deciding whether to retry.

The Node library refuses replacement with `DB_NATIVE_FILE_BUSY` while a database
or batch remains open through the same runtime, including a filesystem alias.
Close those handles first. Other processes must also release the destination
before replacement.

## Planning a large import

Allow space for the captured review batch, the working database, transaction
files, and temporary engine storage. The database retains captured source
evidence alongside typed destination rows, so its size can exceed the compressed
Excel inputs substantially. Recording another batch of an existing capture
reuses that evidence.

The native pipeline has been measured with a generated one-million-row workbook.
That run took about 15 seconds to capture, 2 seconds to review captured values,
and 13 seconds to apply to DuckDB. Its initial database occupied about 108 MB.
Sampled process memory during apply reached about 876 MB in a process warmed by
the smaller benchmark. These measurements depend on row width, strings,
constraints, storage, and concurrent work. They do not establish a browser
capacity limit.

Start with a representative workbook, review its inferred types and row counts,
then increase the batch size. Use the CLI when browser storage or memory
prevents an import. Excel formula cells supply saved results; ConsultChimps does
not recalculate formulas during capture.
